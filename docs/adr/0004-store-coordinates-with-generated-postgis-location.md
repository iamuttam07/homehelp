# 4. Store coordinates with a generated PostGIS location

- **Status:** Accepted
- **Date:** 2026-11-17

## Context

Addresses need a location so providers can later be matched by distance (PostGIS, see ADR 0002). Mapping PostGIS types in JPA requires `hibernate-spatial` and JTS geometry classes throughout the code, and Hibernate's schema validation is unreliable with `geography` columns. The API itself only needs plain latitude and longitude. There is no geocoding service yet; the frontend supplies coordinates from its map or geocoder.

## Decision

- Addresses store `latitude` and `longitude` as ordinary `DOUBLE PRECISION` columns, which the `Address` entity maps.
- A `location GEOGRAPHY(Point, 4326)` column is **generated by the database** from them (`GENERATED ALWAYS AS ... STORED`) and has a GIST index. The entity does not map it.
- Distance and radius queries (provider matching) use `location` through native SQL.
- Coordinates are validated on input (-90 to 90, -180 to 180) and by database check constraints.

## Consequences

- The Java code has no spatial dependencies, and `location` can never disagree with the coordinates.
- Spatial queries must be written as native SQL rather than JPQL.
- The location is only as accurate as the coordinates the client sends. A server-side geocoder could be added later without changing the schema.
